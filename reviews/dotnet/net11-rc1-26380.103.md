## 1. Framing

This edition reviews **SDK 11.0.100-rc.1.26380.103** (daily build 26380.103, 2026-07-30
in Microsoft's date-coded build scheme) — the first build I have tested from the RC 1
line after the branch cut; the preview-7 branch is now in stabilization. Prior editions
are frozen as published; every prior finding is retested here and marked **FIXED**,
**IMPROVED**, or **UNCHANGED**.

This edition is deliberately shorter on prose and centered on performance (section 7).
The conformance ledger (section 5) records verdicts and moves on.

## 2. Executive Summary

- **totalOrder arrived, and it is conformant.** `TotalOrderIeee754Comparer<Decimal128>`
  now implements the one clause it was missing — cohort members ordered by exponent —
  and all **2,702** total-order vectors in the conformance corpus pass (section 5.5).
- **The quantum-preserving ToString fix is merged upstream** (dotnet/runtime PR #131422,
  merged hours after this build's snapshot) — not in this build, so the clause 5.12
  finding formally stands, but recommendation 1 of the prior edition is in flight and I
  expect **FIXED** next edition (section 5.3).
- **The conformance sweep is GREEN at its widest yet: 53,899 vectors run, 0 fail** —
  the prior edition's 51,197 plus the newly-runnable total-order vectors.
- **Comparison cohort change:** System.Decimal is retired from the tables, and the port
  column is now **decimal128-csharp-bid**, my BID128-native C# implementation — all
  three columns operate on the same interchange encoding (section 3).
- **Performance: RC 1 is flat.** Over the 38 cells comparable to the prior edition,
  the geomean build-over-build ratio is **0.984**. The only attributed movement is a
  real 5–8% improvement on the shallow add/subtract paths (verified by same-day A/B
  against the prior SDK; section 7), and FMA drifted about 5% the other way. Every
  pathological band called out last edition — far-quantum add/sub, wide multiply,
  exact/power-of-ten divide, FMA — ships in RC 1 unchanged. After the preview-7
  window's 4× divide step, the optimization phase appears to be over (section 7).

## 3. Scope & Methodology

- **Version under test:** .NET 11 RC 1 line, SDK **11.0.100-rc.1.26380.103**.
- **Harness:** the same standards-anchored rosetta dispatch as the prior edition, now
  also driving the total-order operations through `TotalOrderIeee754Comparer` (the
  comparer is .NET's clause 5.10 vehicle; `CompareTo` remains a value order by design).
  Every bit-level verdict flows through Microsoft's own clause 5.5.2
  `DecodeBinary`/`EncodeBinary`, as established last edition.
- **Comparison cohort — changed this edition:**
  `System.Numerics.Decimal128` (system under test), **Intel libbid**, and
  **decimal128-csharp-bid** — my own C# implementation, BID128-native in memory,
  arithmetic on undecoded operands, non-canonical inputs handled in every operation.
  All three implementations therefore compute directly on the IEEE 754 BID128
  encoding. `System.Decimal` is retired: it is a 96-bit, 28-digit type with no
  Inf/NaN/subnormal story, and its presence in prior tables answered a question
  ("what does the incumbent cost?") this series has now answered twice.
  The port column is **not comparable** to prior editions' `decimal128-csharp`
  column (different implementation); the Decimal128 (.NET 11) column **is**
  comparable build-over-build (identical corpus and methodology).
- **Benchmark pairing:** the Decimal128 (.NET 11) and decimal128-csharp-bid rows come
  from the **same emit run under the same rc.1 SDK**, one process per cell (tier-1/PGO
  code is per-process and training-order-dependent). libbid is C-hosted and
  runtime-independent; on x86-64 the libbid column was nevertheless **re-measured in
  the same session** as the other two, because that machine exhibits day-scale drift
  that would otherwise flatter cross-day comparisons (the M3's same-day repeatability
  makes this unnecessary on arm64). Corpus and bands are identical to the 26376.106
  edition (sign-split add/sub datasets; mul/div/FMA bands unchanged).
- **Reproducibility:** decimal128-csharp-bid is the engine under
  `github.com/migueldecimal128/decimal128-csharp-bid`, commit `e12cb6e`.

## 4. What They Got Right

- Everything from the prior editions stands: numerically correct required arithmetic,
  canonical BID encoding, honest subnormals, truly-fused `FusedMultiplyAdd`
  (re-verified on this build), correctly-rounded `Sqrt` and `RootN`.
- **totalOrder was finished properly, and finished before GA** — exactly the window the
  prior edition argued for, since after GA the cohort-collapsing behavior would have
  become observable behavior someone depends on. Runtime PRs #131087/#131205 gave the
  generic comparer real decimal cohort ordering plus fast paths for the built-in
  decimal types.

### 5.1 Rounding — UNCHANGED

Arithmetic rounds tiesToEven only; no rounding-attribute surface; composing directed
results from already-rounded arithmetic double-rounds. The standing long-horizon item
of this series — restated so the series keeps measuring it, not because this edition
expected motion (see section 8.2).

### 5.2 Flags — UNCHANGED

No status-flag surface; the harness still runs value-only. The confidence-cost
argument from the first edition stands verbatim.

### 5.3 String conversion (clause 5.12) — UNCHANGED in this build; fix merged upstream

This build still renders no scientific notation on any of the formatting paths probed
last edition (`MaxValue.ToString()` is still 6,145 characters; `1E+2` still prints as
`100`; `Parse(x.ToString("R"))` still loses the quantum). But dotnet/runtime PR
**#131422** — "Ensure that Decimal32/64/128 ToString roundtrips and preserves the
cohort" — merged 2026-07-30, hours after this build's runtime snapshot. The finding
stands against the build under test; I expect to mark it FIXED next edition.

### 5.4 fusedMultiplyAdd — STANDS FIXED

Re-verified on this build: single rounding across the sweep's FMA vectors, bit-exact.
`MultiplyAddEstimate` still exists alongside; its fate remains the API-hygiene question
noted last edition (section 8.1).

### 5.5 totalOrder (clause 5.10) — FIXED

The prior edition found the comparer's generic path returning 0 for cohort members,
with a TODO in the shipped source. RC 1 closes it: runtime PRs **#131087** and
**#131205** give `TotalOrderIeee754Comparer<T>` real decimal semantics. My harness now
drives the full total-order corpus through the comparer — 3-way `comparetotal`/
`comparetotmag` and the boolean totalOrder predicates — and **all 2,702 reachable
vectors pass**: cohort members ordered by exponent in both signs, −0 before +0, NaN
placement at both extremes, payload-ordered NaNs. There is still no `TotalOrder`
method on `Decimal128` itself, and `CompareTo` remains (correctly, for .NET) a value
order — the comparer is the standard vehicle, and it is now a conformant one.

### 5.6 Clause 9.2 recommended functions — UNCHANGED

Same verdict and same counts as last edition: `Exp`/`Pow`/`RootN` faithfully rounded
(sporadic last-place misses, counted in the sweep), exact results returned as the
full-precision cohort member where GDAS prescribes the ideal exponent. Correctly
rounded remains the bar that matters for a 34-digit format; the counts did not move.

### 5.7 Log/Log2/Log10 near 1 — UNCHANGED

`Log(1 + 1e-28)` still comes back with about 10 correct digits; `LogP1` on the same
engine is still flawless, so the `LogP1(x − 1)` workaround stands. The binary working
format conversion diagnosed last edition is unchanged. For the log-return arithmetic
this type targets, this remains the accuracy finding to watch.

### 5.8 RootN (own-bug disclosure) — port fix in progress

Last edition disclosed that Microsoft's `RootN` with negative n is correctly rounded
where my implementations are 1–2 ulp off. That bug remains on my punchlist (fix and
oracle regeneration in progress); nothing in this edition's tables depends on `RootN`.

## 6. Permitted & Intentional Divergences — unchanged

Non-canonical propagation through the clause 5.5.2 re-encoding operations (permitted),
the min/max cohort-member choice (158 cases, permitted per the clause 9.6 NOTE), and
the negative canonical NaN (implementation-defined) all reproduce exactly as published.

## 7. Performance

The performance story of this build is that there is not one — and two builds from a
code freeze, that is itself the finding. Between the last preview-7 daily and this
first RC 1 daily, the geomean over the 38 comparable cells is **0.984**: no divide
step this time, no new fast paths, the same band structure everywhere.

Attribution, same methodology as last edition: the prior SDK is still installed
side-by-side, so any cell that moved gets re-run under both runtimes against the same
fixed binary and corpus, on the same day. The M3's repeatability makes this sharp —
today's preview-7 numbers reproduce the published edition's tables to three digits
(Add MIX 9.65 vs 9.67 published; Add SQss 11.92 vs 11.93; FMA FN 1.941 µs vs 1.944).
Against that baseline:

- **The shallow add/subtract paths genuinely improved ~5–8%** (Add MIX 9.65 → 8.83;
  Sub MIX 9.86 → 9.19; Add SQss 11.92 → 11.28). This is a runtime change, not machine
  drift. A plausible candidate landed in this build's snapshot — dotnet/runtime PR
  #131345, which moved Decimal32/64/128 to proper ABI packing in the VM and type
  system — but I have not disassembled to confirm, and the effect size is modest
  either way.
- **FMA drifted ~5% slower** (FN 1.941 → 2.043 µs, FF similar). On a
  microsecond-scale cell I would normally call that noise, but it reproduces in both
  FMA regimes.
- Everything else is within ±5%, including every divide band.

What did *not* change matters more than what did. The strip-loop signature diagnosed
last edition is intact: exact-quotient and power-of-ten divides — the bands with the
least mathematical work in them — still cost ~95 ns, roughly double the width-generic
CD/WD bands and ~8× Intel's libbid, because the trailing-zero strip still removes one
digit per iteration. Far-quantum add/sub still costs ~750 ns against libbid's ~9. Wide
multiply still fails both of the preview-7 window's fast-path guards and runs ~750 ns.
FMA still runs the wide machinery end-to-end at 2.0–2.4 µs. The conclusion from last
edition stands verbatim: within the one-limb design constraint, the tuning that was
available has been taken; the next multiple is an algorithm change, and RC is not
where algorithm changes land. Unless something unexpected happens post-GA, this is
the performance profile .NET 11 ships.

A reading note for the tables: the port column is decimal128-csharp-bid (section 3) —
same-run, same-SDK as the Decimal128 column. Where a number is needed as an external
yardstick, use the libbid column; the Cornea et al. paper cited last edition remains
the standing description of what a mature software implementation of this format does.

## 8. Recommendations

### 8.1 Now — before GA

1. **Ship the merged ToString fix in an RC build** (#131422, section 5.3) — the last
   of the prior edition's three pre-GA recommendations; the work is done, it needs to
   flow into a build so it can be verified.
2. **API hygiene**: decide `MultiplyAddEstimate`'s fate now that `FusedMultiplyAdd`
   exists (unchanged from last edition; GA locks surfaces in).

### 8.2 Later — after GA (additive, non-breaking)

- **Rounding attributes for arithmetic** (section 5.1): the standing long-horizon item.
- **Status flags** (section 5.2): still the cheapest independent verification channel.
- **Near-1 logarithm accuracy** (section 5.7): architectural, committed for .NET 11;
  the `LogP1` workaround carries users until a decimal-native evaluation path exists.

## 9. Conclusion

RC 1 is what an RC should be: conformance work landing (totalOrder finished properly,
the ToString cohort fix merged and queued), correctness holding at 53,899 vectors
green, and performance stationary. The type that ships in November now looks knowable:
correct tiesToEven arithmetic, a conformant totalOrder, competitive compact-path
performance — and the wide-path and divide economics documented in section 7, which I
expect to be GA's performance profile. The long-horizon items (rounding attributes,
status flags, near-1 logarithms) carry forward. I wish the team a quiet freeze.
