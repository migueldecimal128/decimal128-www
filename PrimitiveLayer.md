# The Primitive Arithmetic Layer for Multiplatform Decimal128

*First draft — companion to "Core Architecture and the Cross-Language Constraint Regime for Multiplatform Decimal128"*

## 1. Purpose and Scope

This document specifies the **primitive 128/256 arithmetic layer** promised by the parent architecture document (Sections 4.6 and 11): the uniform API of basic unsigned 128-bit and 256-bit integer operations that every core implementation consumes, together with the rules governing its per-platform, hand-written implementations. It is the one layer where the cross-language constraint regime deliberately relaxes — native 128-bit types, explicit unsigned casts, and platform intrinsics live here and nowhere else.

It covers: the two-tier structure of the layer; the boundary between primitive and core (with the full classification decision log); the U128/U256 arithmetic vocabulary that core code must use in place of native 128-bit expressions; result aggregates and return mechanics; naming; and per-platform implementation notes for Swift, C, Kotlin Multiplatform, and Java.

It does **not** cover the division algorithms (Barrett, Knuth D, range-reciprocal mulPow10, power-of-ten dispatch) — those are core, not primitive, by settled decision — nor the UBD representation, rounding/finalize semantics, DecContext propagation, or translation tooling. Those remain the subjects of the parent document and its other companions.

## 2. Decision Log

The classifications in this document were settled as explicit decisions (June 2026), recorded here so they read as commitments rather than emergent prose. Later sections elaborate each one.

| # | Decision |
|---|---|
| D1 | The layer is **two-tier**: tier 0 = the irreducible per-platform operations; tier 1 = multi-word kernels with a uniform API and platform-honest bodies. Core consumes the union; the tiers describe implementation provenance, not visibility. |
| D2 | `subAbs` (U256−U128 and U256−U256 forms) is a **tier-1 primitive** returning a typed `Diff256Swap` aggregate. |
| D3 | **Simple division** — `divRem_q256r64_256x64` (today's `u256DivRem64`) together with everything below it (fast paths, divisor-width dispatch, the divMod{64,128,192,256}x{16,32} kernels, `divRem256by64`) — is one self-contained tier-1 unit. `u256DivRem128`, `u256DivRem_128`, and residue computation remain **core** (`u256DivRem256` was later retired — D35). |
| D4 | The **mulPow10 family** — plain `mulPow10` plus `fusedMulPow10Add` and `fusedMulPow10SubAbs` — is tier-1: it is performance-critical and benefits from platform-specific tuning. The `POW10`/`POW10_256` tables are defined at the primitive layer as read-only constants, directly readable by core. |
| D5 | The parent Section 4.2 confinement rule is **enforced**: core code routes all U128 arithmetic expressions through a tier-1 vocabulary of uniformly named functions. Swift retains `UInt128` as the *physical* representation of U128, with computed `.dw0`/`.dw1` accessors providing the uniform dword surface. |
| D6 | The **calcBitLen/calcDigitLen family** (128- and 256-bit forms, including the `WithBitLen` variants) is tier-1. `calcDigitLen` is performance-critical and requires unsigned compares that Kotlin/Java cannot express directly. Tier 0 gains `clz_int_64`. |
| D7 | **bitLen/digitLen are recomputed, never cached.** Magnitude types carry dwords only. Kotlin's `steal` packed-lengths field (and its packed-zero-flag trick) is removed during the Kotlin rework. |
| D8 | **Fill-in parameter order: destination first, scratch/ctx last** — `op(result, operand…, scratch/ctx…)`. Keeps operand order identical to the Swift/C value-return line, holds the destination at position 0 under varying arity, and matches the existing Kotlin kernels and C precedent. |
| D9 | **Names lead with the result, in full segment form throughout the uniform API**: `op_result_operands[_qualifier]` — `divRem_q256r64_256x64`, `add_256_256x64`, `subAbs_d256swap_256x128`. Type-prefix abbreviations were considered and rejected. Tier-0 scalar ops were originally excepted with inline-width short names; D11 retires that exception and folds them into the grammar. |
| D10 | **`barrettStep` is promoted to tier 1** as `divRem_q64r64_64x64x64_mu_barrettStep`, reversing its Section 4.3 retention. The single reciprocal-multiply division step is decimal-agnostic, and its branch-free correction is exactly the Section 6.2 confined idiom — keeping it core would force that idiom into JVM-family core source. Barrett *strategy* — the mu tables, the 10^k = 2^k·5^k split, dividend-width dispatch, and the chunk-kernel ladder — remains core. |
| D11 | **Tier-0 names fold into the D9 segment grammar**, retiring the inline-width exception: `umulHi_64_64x64`, `udiv_64_64x64`, `urem_64_64x64`, `ucmp_int_64x64`, `ushr_64_64`, `clz_int_64` — count of leading zeros — (and `ntz_int_64` — number of trailing zeros — if confirmed). The `u` op prefix marks the unsigned semantics that signed dwords obscure — information the 128/256 families don't need (their types are unsigned) but 64-bit ops do (signed dwords have two real shifts and compares). The exception had eroded: the set outgrew "five ops, learned once," and `ucmp_int_64x64`/`cmp_int_128x128`, `ushr_64_64`/`shr_128_128`/`shr_256_256` now form one grammar instead of two systems. |
| D12 | **The U128 vocabulary is frozen.** The Section 5.3 confinement sweep of the Swift reference is complete (June 2026); per the rule that the sweep is the authority, membership is fixed at the twelve Section 4.2 ops plus `mul_128_64x64` (later eleven, after D31 retired `xor_128_128x128` as unused). **U128 vocabulary arithmetic is wrapping** (bit-bucket semantics, matching the native `&+`/`&-`/`&*` expressions it replaced); trap-on-overflow exists only in the U256 family. Expression forms the sweep found but deferred are tracked as candidate members in Open Items: the sign-mask/conditional-negate idiom, 128÷128 divRem, and the `hi32`/`lo32` dword half-word ops. |
| D13 | **`hi32_64`/`lo32_64` join tier 0**, resolving the half-word question in favor of dedicated ops over bare `ushr_64_64` spellings: the high half of an arbitrary dword is the dominant logical-shift shape in the kernels (Knuth loads, Barrett 32-bit chunking), and the named pair reads as intent where a shift count reads as arithmetic. The logical-shift confinement pass is complete in the Swift reference — field/flag extraction (ubd predicates, BID/DPD words, residue sign checks) and chunk-boundary shifts spell `ushr_64_64`; half-word extraction spells `hi32_64`/`lo32_64` — except the rrmp10 kernel interiors, which await the Section 3.4 exemption decision. |
| D14 | **subAbs extends to 128 bits**: `subAbs_d128swap_128x128` returning `Diff128Swap` joins the D2 family. The confinement sweep's deferred sign-mask/conditional-negate idiom was recognized as subAbs in disguise — all five core sites computed |x−y| plus a swapped flag. With this member the idiom is spelled only inside primitive bodies (per parent Section 4.3), and the Swift body needs no signed cast at all: the borrow flag of the subtract is the swapped flag. |
| D15 | **`divRem_q128r128_128x128` joins the division family** (returning `Quot128Rem128`), and the table's `divRem_q128r64_128x64` is implemented; core's last four native `quotientAndRemainder` sites convert. With D14 and the deletion of the unused `d128_coeffSigned` accessor, the confinement sweep is complete: core contains no native 128-bit arithmetic outside `verify` closures. JVM bodies need no Knuth D: the 128÷64 form is the divlu kernel; the 128÷128 form delegates to it (divisor < 2^64) or clz-normalizes and corrects one estimate (divisor ≥ 2^64, quotient fits 64 bits). |
| D16 | **The rrmp10 kernels are promoted to tier 1** behind two uniform entry points (`divPow10_q128rs_128_rrmp10`, `divPow10_q128rs_256_rrmp10`) returning the new dword-only aggregate `Quot128RoundSticky` — a 128-bit quotient plus *raw* rounding inputs (round bit, sticky compare, pre-shift sticky bits). The quotient is 128-bit **by contract**: rrmp10 reduces to 34/38 digits (256-bit dividends) or ≤18 digits (128-bit path), and the entries demand the fit — the earlier 256-bit return shape was a legacy of the Kotlin implementation's full 256-bit mutable surface, which is being discarded. Core categorizes the raw bits into a `Residue`, so rounding semantics stay core; strategy (digitLen range demands, the digitLen→pIndex choice) stays core. **All shared read-only tables now live at the primitive layer** — the RRMP10 params *and* lookups join POW10/POW10_256/POW5_64 — because primitive residence gives each platform its native table spelling: multiplier limbs with bit 63 set stay unsigned on Swift/C (signed-Long bit patterns on the JVM), and byte-packed lookup values above 127 avoid the JVM's signed-byte masking. Refinement of D4: dword-and-wider tables remain directly readable by core; sub-dword tables are read through Int-returning accessor functions (`rrmp10Lookup128` etc.), since a direct byte read cannot be spelled uniformly. |
| D17 | **Residue de-structs to a 2-bit Int**, defined at the primitive layer: `RESIDUE_EXACT/LT_HALF/HALF/GT_HALF` = 0–3, encoding frozen as `(round << 1) | sticky` — the universal IEEE round/sticky pair, direction-free and base-free. Java cannot express a zero-cost wrapper, so under line-for-line translatability the wrapper was unrepresentable on one core anyway; a residue is a 2-bit bucket, the same move as signed dwords. Operations verify the low-2-bits invariant; four values keep it human-debuggable. Consequences: `Quot128Residue`/`Quot256Residue` become dword-only by shape and join their primitive-layer siblings (the Section 6.3 exception evaporates rather than being reversed — its premise is gone); the rrmp10 entry points return `Quot128Residue` directly, superseding D16's raw-bits seam (`Quot128RoundSticky` is deleted); the residue classification helpers remain core *code*, movable per-function. Direction semantics — `needsRoundUp` and the rounding maps — are core, always. |
| D18 | **`Stripped128StripCount` settles the strip result shape**: a typed aggregate (`stripped128`, `stripCount`), resolving the open typed-aggregate-vs-loose-tuple question in favor of family consistency — returned by value on Swift/C and by caller-supplied fill-in on the JVM family, like every aggregate (Section 6.4; the EA-value-return contingency this entry once weighed is moot under the fill-in convention). At three dwords it is the smallest aggregate in the family. The tuple it replaces was the last in the layer's orbit. The function's full-form D9 spelling and its relocation (the Swift body still calls core's 128-bit Barrett pow10 unit) remain open. |
| D19 | **The magic ÷10 divide is promoted to tier 1** as `div1e1_q128res_128_magic`: a fixed-reciprocal high-word multiply — the `barrettStep` pattern with a hardcoded constant — and the last divPow10 method whose mechanics lived in core (rrmp10's were promoted by D16, the direct method composes from the D15 divRem primitives). `residueFromDecimalDigit` (the two-bits-per-digit map, pure mechanics) moves with it, the first classification helper to take the per-function mobility D17 granted. `DivPow10`'s method dispatch and the `q*res` wrappers remain core: with this, every divide-by-pow10 *method* is primitive mechanics and core is purely the chooser. |
| D20 | **The 128-bit exact-remainder Barrett pow10 unit is promoted to tier 1** as `divPow10_q128r64_128_barrett` (with the 32-bit chunk kernel and the `BARRETT_POW5_MU` table — closing the D16 all-tables debt — and `BARRETT_POW10_MAX`), and **strip relocates** as `strip_s128sc_128`, making the inherited "strip is primitive" classification physical at last. The unit is residue-free, contains no strategy (fixed range, one kernel), and after D10 called only downward. Deliberately **not** taken: the 256-bit twin `divPow10_q256r64_256_barrett` and its chunk ladder (the 128/256 asymmetry is recorded interim, promotable by the same reasoning), the `q*res` wrappers and `_loop` composition (core, dispatch arms), and Knuth D (same gradient, no forcing function). |
| D21 | **`ntz_int_64` is folded into platform-local bodies**, resolving the open tier-0 proposal by declination: after D20, every trailing-zeros consumer (strip's bulk and tail loops, the power-of-two divisor path) lives inside a platform-honest primitive body, where each platform spells the operation natively — no uniform-source code needs the name. The contrast with `clz_int_64` is the principle: clz earned its row because the common-source length-family kernels consume it by name; a tier-0 entry nothing above the line consumes would dilute what the table means. Reverses cheaply if a uniform-API consumer ever materializes. Companion fix: core Knuth D's three normalization-shift sites now consume `clz_int_64` by name — the tier-0 entry's first actual callers, completing Section 3.1's claim that core consumes tier 0 by uniform name. |
| D22 | **The length family takes its full-grammar names**: `bitLen_int_128`, `digitLen_int_128`, `digitLen_int_128_withBitLen`, `bitLen_int_256`, `digitLen_int_256`, `digitLen_int_256_withBitLen` (formerly the `calcBitLen*`/`calcDigitLen*` spellings), resolving the table's last ◆ marks — the `int`/`bool` result segments are confirmed, as D11–D21 practice already established (`cmp_int_128x128`, `clz_int_64`, `isZero_bool_128`). The platform-local Int helpers (`calcBitLenInt`, `calcDigitLenInt`, `calcDigitLen64`) keep their names per D6: they are decomposition, not contract. |
| D23 | **Limb parameters ascend: dw0 first.** Where U128/U256 values cross the uniform API as discrete dword limbs (the long/int64 parameter surface adopted for portability — no 128-bit type at the boundary), positional order in every signature is little-endian — `(dw0, dw1)`, `(dw0, dw1, dw2, dw3)` — and result aggregates declare their low limb first. The order is load-bearing, not stylistic: LLVM splits `i128` low-half-first into argument *and* return registers on arm64 and x86-64 alike, so an ascending decompose→pass compiles to a bare tail-branch (zero moves, verified by asm probe) and reconstruction on the far side is free — the limbs already sit in return position — while descending order costs a three-instruction swap at every non-inlined boundary. The C peer port gets the same answer plus a bonus: discrete `uint64_t` limbs escape AAPCS64's even-register-pair alignment rule for `__int128`. Documentation and comments may still render values big-endian (`dw3‖dw2‖dw1‖dw0`); the decision binds signature positions only. Existing hi-first spellings (`fromDwords_128_64x64(hi, lo)`, the `U256(dw3:dw2:dw1:dw0:)` constructor) are Swift-local conveniences outside the uniform surface, but converge during the limb-surface sweep. |
| D24 | **The limb surface lands** — the D23 order becomes physical in two moves. (1) **Result carriers store dword limbs**: every Quot*/Diff*/Stripped* aggregate re-stores as role-major ascending dword fields (`quotDw0…`, `remDw0…`, `diffDw0…`, `strippedDw0…`; non-limb scalars keep their plain names and declare last). The **field list — names, types, declaration order — is the uniform cross-platform surface**; constructors and typed accessors are platform-local spellings, so the Swift `U128`/`U256`-accepting inits stay permanently. Core reads carriers by limb fields; the Quot* family's typed sugar accessors are deleted (compiler-enforced limb reads), while the Diff*/Stripped* accessors remain in use pending the same conversion. (2) **The arithmetic core takes limb parameters**: the U128 vocabulary and the U256 add/sub/subAbs/mul families gain limb-form implementations (`xDw0, xDw1, yDw0, yDw1, …` — operand-major, ascending; trailing scalars last; same D9 name, overloaded, arity disambiguating), with Swift bodies that reconstruct native UInt128 immediately. **Core and the tests consume the limb forms exclusively**; the typed overloads survive as **Swift platform-local spellings (§3.4), not uniform API** — Primitive's own bodies (the mulPow10/fused family) keep them, a classification forced by measurement: migrating Primitive-internal call sites regressed codegen (outlined `multipliedFullWidth` specializations, doubled bodies) for zero contract benefit. Two engineering rules were paid for in asm: **platform-local sugar must be self-contained, never delegating** — a typed overload that merely forwards to the limb form inflates pre-optimization SIL and blows inliner budgets downstream (the `<` fast path picked up outlined `d128_u128` calls until the sugar got its direct body back) — and **dword-native rewrites beat mechanical respelling** where the operation is really sub-128-bit (parity as `dw0 & 1`, sign ops as single dw1 bit flips, copySign as a sign-bit transplant that restores the two-instruction `lsr`+`bfi` codegen). Acceptance was a whole-build asm comparison against the pre-migration baseline: all shared symbols byte-equivalent modulo register allocation and trap-location immediates, except a characterized handful (one function improved, two convenience-Int operators one call deeper, and the deliberate `mul_256_256x256` trampoline). |
| D25 | **The fused mulPow10 forms are shrunk away by usage, partially reversing D4.** The caller census after the D24 migration found the family's uniform-API consumers gone: `fusedMulPow10Add_256_256x128` and both `fusedMulPow10SubAbs` forms had zero callers, `fusedMulPow10Add_256_128x128` only a scratch reference. The shapes never fit the rebuilt addWide: when there is a multiply to fuse (m small, shiftLeft > 0) the addend is the 256-bit product side, exceeding every ≤128-bit-addend signature; when the addend fits, there is no multiply (m wide, headroom 0). Completing the family with `_256x256` variants would buy only a JVM holder round-trip on the fma path — and fma carries no performance demand, so no consumer materializes: the D21 declination, applied to D4's own members. All four are deleted; the one true survivor, `fusedMulPow10Add_256_256x64` (the hand-interleaved carry-chain accumulator), is reclassified §3.4 platform-local — its sole consumer is `U256.from`. The deletion cascaded by D24's sharpened existence rule — **a typed overload exists iff a §3.4 platform-local body consumes it** — taking the typed `add_256_256x128` and `subAbs_d256swap_256x128` overloads (their only callers were the deleted fused bodies) and, in the same sweep, the 17 typed arithmetic overloads with no Primitive-interior consumer, leaving five (the mulPow10 interior's mul family — all since downgraded to `internal`, so the §3.4 classification is visibility-enforced, and `mul_256_128x64` folded to interior-only outright: no core consumer means no limb form and no uniform-API row). Compiler-enforced from here: a typed call from core fails to build, and the interior spellings cannot be named outside the module. Plain `mulPow10_128_128`/`_256_128`/`_256_256` are untouched and remain uniform API, on the pass-2 limb-conversion worklist. Reverses cheaply if a uniform-API fused consumer ever materializes. |
| D26 | **Pass 2 completes the limb surface: no uniform-API entry point takes a 128/256-bit typed parameter.** The remaining families convert in sequence — length (`bitLen`/`digitLen`, with the `withBitLen` scalar moving to trailing position per D24's order), mulPow10, divPow10 (magic/barrett/rrmp10 — pure parameter renames, their bodies already limb-spelled), divRem, strip, the 256-bit shifts, and the shared Barrett chunk kernel — each gated by the whole-build asm comparison. The census-verified end state: **zero `package` functions in Primitive with a `U128`/`UInt128`/`U256` parameter**, which is the point of the D23 regime — the uniform API's parameter surface is now spellable verbatim on the JVM family and C, no 128-bit type required at the boundary. Typed spellings survive only as `internal` interior helpers where a §3.4 body consumes them (the D25 existence rule, applied per-op: `mulPow10_128_128` for strip's bulk loop, `divPow10_q128r64_128_barrett` likewise, `divRem256by64` and `shr_256_256` for the 256÷64 dispatch, the `U256.bitLen()`/`digitLen()`/`divRem(UInt64)` method sugar for Primitive interiors). The shared 32-bit Barrett chunk kernel `barrett_128_32_mu_q128r64` is the exception to the `internal` rule: pass 2 converted it to limb form — so it takes no 128/256-bit typed parameter and does not breach the headline claim — but it stays **`package`**, not `internal`, because core's 256-bit Barrett side consumes it (D20), so core must be able to name it. The census also killed dead weight it surfaced (core's uncalled `U256.div`, the consumer-less `U256.divRem(UInt128)`). Gate findings: one attribute restoration (`bitLen_int_256` needed the `@inline(__always)` its deleted method twin had carried — caught as an outlined call in Knuth D), and two functions *improved* (mulPow10 bodies lost an outlined `multipliedFullWidth` specialization). The typed crossings that remain are deliberate, not residue: carrier constructors (platform-local by D24), and `U256`-typed returns and core locals (D5's physical-representation choice) — the agenda items for the JVM-core design. |
| D27 | **The value types store dword limbs: D24's field-list contract extends from the result carriers to the working types themselves.** `Decimal128` re-stores its packed 128-bit UBD value as `ubdLo64`/`ubdHi64` (lo declared first per D23/D24; the names are UBD.md's own vocabulary), and `D38` re-stores its coefficient as `coeffLo64`/`coeffHi64` beside the existing `qExpAndSignBit: Int32`. As with the carriers, the **stored field list — names, types, declaration order — is the uniform cross-platform surface**: a JVM `Decimal128` is two longs named `ubdLo64`/`ubdHi64`, a JVM `D38` two longs and an int — no 128-bit type, no boxing, no translation gap. Constructors and whole-value accessors are platform-local. `Decimal128` keeps a `U128`-accepting init, but **`D38` is now constructed only from limbs** — its two surviving ctors take `(signFlag, qExp, coeffLo64, coeffHi64)` and `(qExpAndSignBit, coeffLo64, coeffHi64)`; the `U128`-accepting `D38` ctor was removed (June 2026), so every D38 finalize/conversion site feeds dword limbs directly. `d128_u128`/`d38_u128` reconstruct the coefficient only where code genuinely consumes 128 bits, and that is now a *signal* — everything else reads the limb it actually touches (`x.ubdLo64`, `d128_hi49(x)` — UBD.md's coeffHi49); e.g. the D38←Decimal128 conversions in the log/exp kernels now read `x.ubdLo64`/`d128_hi49(x)` rather than rebuilding (then immediately unpacking) a `U128`. The old spellings — the single packed 128-bit field, its `hi64`/`lo64` accessors, and `u128` — are deleted, compiler-enforced. The conversion paid for itself in codegen: packing inits dropped their 128-bit shift/or chains for direct dword composition, `D128_POS/NEG_INFINITY` collapsed to constant data (their addressors went from a 33-line call to 9 lines of loads), `ctxSignalDivByZero` shrank 82→31 lines, and the lingering convenience-operator call-depth regression from the D24 migration healed itself — all verified by the standing whole-build asm gate, hot paths byte-equivalent or better. A follow-up hygiene sweep replaced the migration-era `d128_u128(x).dw0/.dw1` double-spellings (~30 sites, byte-identical asm) with the limb-native forms, completing the principle that reconstruction appears in source only where reconstruction happens in meaning. |
| D28 | **`U256` stores four `Int64` limbs** — `dw0`/`dw1`/`dw2`/`dw3`, ascending — completing the working types' move to the signed-limb representation under the **signed-everywhere regime**: dwords cross the uniform API, live in carriers and value types, and are held in core as signed `Int64` on every platform, because that is the only choice under which raw `>>`/`<`/`/`/`%` *mean the same thing* in shared core source as they do on the JVM `long` (the reference must be incapable of expressing a JVM-divergent meaning; unsigned semantics are reached only through named ops — `ushr_64_64`, `ucmp_int_64x64`, `udiv`/`urem`). The signed flip is byte-free: `Int64(bitPattern:)` is a reinterpret, proven across the conversion by the standing asm gate. `U256`'s prior `(lo, hi): UInt128` storage inverts — `.lo`/`.hi` become Swift-local computed accessors (§3.4) reconstructing the `UInt128` halves from limbs; `.dw0…dw3` become stored; `init(dw:)` takes `Int64`, and the `UInt128` `init(hi:lo:)` convenience constructors stay (decomposing to limbs). The field list is the cross-platform surface: a JVM `U256` is four longs with these names. The change was deliberately staged — value-type fields (D27), then carrier fields, then the `.dw` accessors, then this storage flip — each gated, each bridging the not-yet-converted bodies (**DivBarrett, DivKnuth**) with `UInt64(bitPattern:)` reverse-casts so those stay byte-identical and undisturbed. Two engineering notes the gate forced: (1) a `>> 48`/`>> 63`-style fits-check on a now-signed dword silently becomes an arithmetic shift — equivalent inside a `== 0` test but a real instruction change, so such checks are respelled `ushr_64_64(…, 48) == 0` (the logical-intent, portable form); the *deliberately* signed shifts (qExp/D38-qExp decode, sign-mask/borrow/sciExp idioms) are correct as-is and were left. (2) The reconstruct-from-limbs cost is real but confined: `U256.<` and `digitLen_int_256_withBitLen` outline rather than inline on cold paths; it dissolves when the deferred tranche converts `U256.<`/DivBarrett/DivKnuth to limb-native unsigned ops. Open: the **tier-0 dword-return flip** (`ushr`/`umulHi`/`hi32`/`lo32` → return `Int64`), the return-side mirror of the parameter flip, gated behind those same ~26 unsigned-math interior consumers. |
| D29 | **The signed-everywhere regime closes: the deferred tranche and the tier-0 flips land, and core is `Int64`-clean.** D28's two debts clear. (1) **The deferred bodies convert** — `DivBarrett` and `DivKnuth` become limb-native signed `Int64`: the `UInt64(bitPattern:)` reverse-cast bridges are removed, raw logical right-shifts respelled `ushr_64_64`, unsigned magnitude compares `ucmp_int_64x64`, unsigned division `udiv_64_64x64` (a signed `/` would emit a `sdiv`), while the *deliberately* signed carry/borrow arithmetic (`t >> 32` sign-propagation, `tFinal < 0`, the `>> 63` borrow) is left as-is. (2) **The tier-0 dword-return flip** — `umulHi_64_64x64`/`udiv_64_64x64`/`urem_64_64x64`/`ushr_64_64`/`hi32_64`/`lo32_64` now *return* `Int64` (the return-side mirror of the D23 parameter flip; `clz_int_64`/`ucmp_int_64x64` already return `Int`), immediately followed by the **parameter flip**: the §3.4 interior `UInt64`-overload spellings fold into the single `Int64`-in/`Int64`-out signature (the unsigned op is reached only inside the body via `UInt64(bitPattern:)`), so the whole tier-0 surface is now signed both ways. ## 3. The Two-Tier Structure

### 3.1 One API, Two Tiers

The primitive layer presents a single uniform API to core — the same function names and signatures on all four platforms, per parent Section 4.6. Internally that API has two kinds of members, distinguished by where their implementations come from:

- **Tier 0** operations are irreducible: each platform supplies them from intrinsics, stdlib calls, or shims, and no portable expression of them exists at acceptable cost.
- **Tier 1** operations are multi-word kernels *composable* from tier 0, with bodies that are platform-honest (Section 3.3).

Core code may call operations of either tier by their uniform names; the existing cores already do (Swift's core Knuth D consumes `udiv_64_64x64` and `ucmp_int_64x64` directly in its q-hat estimate). The tier boundary constrains implementers, not callers.

This structure is not hypothetical. The Kotlin Multiplatform implementation proved it: its `expect`/`actual` split isolated *all* platform divergence to four unsigned 64-bit operations, with every multi-word kernel built portably above them in common source shared by the JVM, Native, and JS targets.

### 3.2 Tier 0 — The Irreducible Operations

Tier 0 is deliberately tiny, and every tier-0 operation returns a **single value** — no result aggregates, no out-parameters. The multi-value machinery of Section 6 begins at tier 1.

- **Swift and C tier 0 is approximately free.** Their native unsigned types and 128-bit arithmetic provide every tier-0 contract directly, so they need not materialize tier-0 functions at all; their tier-1 bodies simply use native operations. - **Kotlin and Java realize tier 0 differently** — `expect`/`actual` declarations on Kotlin MP, `static` wrappers over JDK intrinsics on Java — but with identical names, so their tier-1 kernel sources stay structurally parallel. This is a sanctioned divergence (Section 9).

### 3.3 Tier 1 — Portable Kernels with Platform-Honest Bodies

Tier 1 is the bulk of the layer: multi-word add/sub/subAbs, the multiply family, mulPow10 and its fused forms, simple division, shifts, the U128 vocabulary (Section 5), bit/digit length, and trailing-zero stripping.

The uniform API — names, signatures, result types, preconditions — is identical on all four platforms. The **bodies** follow the parent document's guiding principle of *parallel structure with platform-honest bodies* (parent Section 3.2):

- **Kotlin MP** writes tier-1 kernels once in common source, in regime-compliant style, shared verbatim across the JVM, Native, and JS targets. All platform divergence stays below, in the tier-0 actuals.
- **Java** mirrors the Kotlin kernel source structurally — same names, same statement shapes — differing only in language syntax.
- **Swift and C** are *sanctioned to implement tier-1 bodies with native 128-bit arithmetic* (`UInt128`, `unsigned __int128`) rather than composing from tier 0. This extends parent sanctioned divergence #3 from "primitives" generally to tier-1 bodies specifically. Where no native advantage exists, Swift/C bodies should mirror the Kotlin kernel structure instead, so that divergence is paid for only where it buys something.

The practical consequence: a tier-1 function has at most **three** body families to maintain and verify — the JVM-family kernel (Kotlin and Java, structurally identical), the Swift body, and the C body — and the latter two are frequently near-identical as well.

### 3.4 Platform-Local Decomposition Is Not Contract

Below the uniform API, each platform decomposes freely. Kotlin's `SumU64.kt` kernels (`sumU64` over 2–9 operands with tree-structured carry propagation, `diffU64`, `umul128x128to192`, …), Swift's private `u64StripTrailingZeroDigits` helper, and the Swift divMod kernel ladder inside the simple-division unit (Section 4.4) are all **internal decomposition**: useful, tuned, and invisible to core. They carry no cross-platform naming or shape obligations, though convergent shapes (and there are striking ones — see Section 8.5 of the operation inventory) are welcome evidence of correctness.

The same applies to loose-dword parameter passing. Kotlin's kernels pass operands as individual `Long` arguments (`x1, x0, y1, y0`) rather than objects — proven efficient on the JVM and consistent with parent Section 4.2's "parameters are passed as the individual dword fields." That style is the *internal* idiom of JVM-family kernel decomposition. The *uniform* API that core calls takes U128/U256 values and returns typed aggregates (Section 6).

## 4. The Layer Boundary

### 4.1 The Classification Rule

The primitive layer contains **basic 128/256-bit integer operations**; the core contains **algorithms and strategy**. The line, applied across every decided case:

- A *loop or carry chain over limbs* with no decimal semantics → primitive.
- A *choice among methods* (which algorithm, which table, which width class — when the choice encodes numeric strategy) → core.
- Decimal-*flavored* but mechanically basic and performance-critical (strip, mulPow10, digitLen) → primitive, because these benefit from per-platform tuning and sit on hot paths.
- Decimal-*semantic* (residue categorization, rounding, finalize, parse/print) → core, always.

### 4.4 The Simple-Division Unit

`divRem_q256r64_256x64` (today's `u256DivRem64`) is the layer's one large composite primitive, and D3 fixes its boundary by call direction: it calls only downward, so the whole ladder ships as one unit behind one uniform entry point.

The Swift reference structure, which other platforms may mirror or re-tune:

1. Fast paths: divisor ≤ 1 (trap on 0, identity on 1); dividend fits 64 bits (single hardware divide); power-of-two divisor (shift + mask via trailing-zero count).
2. Divisor-width dispatch: ≤16-bit and ≤32-bit divisors route to specialized limb kernels (`divMod{64,128,192,256}x{16,32}`), selected by dividend bit length.
3. 33–64-bit divisors: 4-step base-2⁶⁴ long division (`divRem256by64`), one `dividingFullWidth`-contract step per limb.

Everything inside is platform-local decomposition (Section 3.4): the kernel ladder is Swift's tuning, not contract. The contract is the entry point's behavior: full 256÷64 quotient and 64-bit remainder, divisor nonzero.

Its production consumer today is general decimal division (via core's `u256DivRem_128` strategy wrapper) — small divisor *coefficients* (÷2, ÷3, ÷100) in ordinary division. The pow10 paths never reach it; Barrett and rrmp10 own those in core.

### 4.5 The mulPow10 Family and the POW10 Tables

mulPow10 is hot enough, and shaped conveniently enough per platform, that the whole family is tier-1 (D4). Swift already hand-interleaves the limb products of `fusedMulPow10Add` with the addend's carry chain; the JVM family composes `umul128xPow10`-style kernels from `umulHi_64_64x64`; platforms without an advantage may implement the fused forms as plain mulPow10-then-add/subAbs sequencing. All of that is body freedom under one API.

The 10⁰…10⁷⁷ powers of ten are **defined at the primitive layer** as a read-only constant used by core for digitLen comparisons and division pow10 dispatch. They are shared constants with identical values everywhere, not an ownership wall. **D30 flattened the storage to signed-`Int64` limbs; D33 consolidates it to a single store:** one `POW10` array of 256 limbs holds Region A — 10⁰…10³⁸ as lo/hi pairs at `POW10[p<<1]`/`[(p<<1)|1]` (offsets 0…77) — and Region B — 10³⁹…10⁷⁷ as four-limb quads at `POW10[POW10_QUAD_BASE + ((p-39)<<2) …]`, `POW10_QUAD_BASE = 78` (offsets 78…233) — followed by a 22-limb zero tail to round the store to 256. The store is byte-identical across the C/JVM/Swift ports, and core reads it through the **width-marked dword accessors** `pow10_128_dw0`/`pow10_128_dw1` (Region A; carrying a `verify(p ≤ 38)` domain guard) and `pow10_256_dw0…dw3` (Region B) rather than a typed 128-bit element — the same dword-surface discipline the rest of the layer adopted, replacing D4's original direct-typed-read. Each accessor masks its final limb index with `POW10_BCE` (now `0xFF`, since the store is 256 limbs), so every read is bounds-check-eliminated by construction. **D34 fills the tail:** `POW5_64` (5⁰…5¹³) folds into offsets 234…247 (`POW5_64_BASE = 234`), read through `pow5_64(p)` over the same `& 0xFF` mask, leaving 8 pad longs — so the only standalone power tables left are `BARRETT_POW5_MU` and the RRMP10 lookups. D16 generalizes the residence rule: **all shared read-only tables live at the primitive layer** (POW5_64 and the RRMP10 tables included), with sub-dword tables (the byte-packed RRMP10 lookups) read through Int-returning accessors, because a direct byte-element read cannot be spelled uniformly on signed-Long platforms.

### 4.6 Length Calculation: Recompute, Never Cache

The length family — `bitLen_int_*`/`digitLen_int_*` (formerly `calcBitLen*`/`calcDigitLen*`; renamed by D22) — is tier-1 (D6). digitLen is the classic two-step: `(bitLen × 1233) >> 12` for a floor estimate, then one unsigned table compare against `POW10` — and that unsigned compare is exactly what Kotlin/Java cannot write natively, which is what pushed the family into this layer. bitLen composes from `clz_int_64` with the branch-free two-word idiom (Section 6.2). The scalar member `digitLen_int_32` (D32; the exponent-sizing digit count used by `D128Print`) joins the family; the remaining `calc*` Int helpers (`calcBitLenInt`, `calcDigitLen64`) stay platform-local decomposition, not contract (D22).

D7 makes the storage rule explicit: **magnitude types carry dwords only, and lengths are always recomputed.** The Kotlin implementation's `steal` field — cached bitLen/digitLen packed into C256's heap-padding Int, doubling as a zero flag — is removed during its architecture rework. The reasoning: clz is 1–2 cycles everywhere; a cache imposes a maintain-the-invariant obligation on every mutating kernel (a standing JVM-only bug source, invisible at call sites); and a cache field would force a fifth dword-sized member into the Swift/C value structs, violating the four-dword shape of parent Section 4.2. If profiling later shows a hot recompute, caching may return as a measured, localized optimization — not as the default.

## 5. The U128/U256 Core Vocabulary

### 5.1 The Confinement Rule, Enforced

Parent Section 4.2 states that native 128-bit machine types appear only inside the bodies of arithmetic primitives. D5 resolves how that rule meets reality: **it is enforced, by giving core a complete vocabulary of uniformly named U128 operations** — `add_128_128x128`, `shl_128_128`, `and_128_128x128`, `cmp_int_128x128`, and the rest of the Section 4.2 table — and requiring core to express all 128-bit arithmetic through it.

On Swift and C the vocabulary functions are always-inline wrappers over native 128-bit operations, observed (Swift) and expected (C) to compile to zero runtime cost. On Kotlin and Java they are the synthesized Long-pair kernels. The result is that the ~10 core files that today perform direct `UInt128` mask/shift/compare/wrapping arithmetic — `D128.swift` (ubd packing), `D128ArithAddSub`, `D128ArithMul`, `D128ArithFma`, `D128Parse`, `D128SerdBid`, `D128SerdeDpd`, `D38AddSub`, `D128ToIntegral`, `Finalize` — become expression-level translatable: their future Kotlin/Java translations match line for line precisely in the bit-trickiest code, where mutual verification matters most. The cost is a one-time mechanical sweep of those files.

### 5.2 Representation: Behavioral Dwords

`U128` and `U256` are **defined at the primitive layer**: the type definitions, their accessor bodies, and their representation choices live with the arithmetic that owns them. Core consumes the types through their uniform dword surface and never sees what is behind it.

The vocabulary decision lets the *representation* question land gently:

- **Kotlin and Java:** U128/U256 are final mutable classes of stored signed-Long dwords, per parent Section 4.2 — unchanged.
- **C:** U128/U256 are structs of `int64_t` dwords. C has no computed properties, so the dword fields must be physically real; bodies pack to `unsigned __int128` and unpack, which C compilers are expected to fuse.
- **Swift:** U128 keeps **`UInt128` as its physical representation**, with computed `.dw0`/`.dw1` accessors (mask, shift-by-64) providing the dword surface. Core source reads `x.dw0` identically on all four platforms; whether that is a stored field or a zero-cost computed property is confined to the accessor body — itself primitive-layer territory. The computed-accessor exception was already sanctioned during the accessor sweep (`dw0`/`dw1`/`hi64`/`lo64` remain computed vars); D5 makes it load-bearing.

The parent Section 4.2 "dword restructure" of Swift's U128 is therefore satisfied *behaviorally* rather than physically, and is no longer pending as a physical change. U256 on Swift remains hi/lo-of-UInt128 physically with `dw0…dw3` computed accessors, by the same reasoning.

### 5.3 What the Sweep Changes

For the Swift core, enforcement means:

- Native U128 expressions in core files (`a &+ b`, `x >> 110`, `x & mask`, `x < y`) are rewritten as vocabulary calls (`add_128_128x128(a, b)`, `shr_128_128(x, 110)`, `and_128_128x128(x, mask)`, `cmp_int_128x128(x, y) < 0`).
- The U256 *method* surface (`x.add(y)`, `x.mul(y)`, `x.subAbs(y)`) migrates to top-level functions (`add_256_256x256(x, y)`, …), because the uniform API must be expressible in C, which has no methods, and the regime's restrict-to list already names "static and top-level functions" as the shape of core code.
- Core files keep reading `.dw0…dw3`, `.bitLen()`/`.digitLen()` (or their top-level spellings) — accessor reads are not arithmetic and are uniform already.

The vocabulary's exact membership was derived mechanically: the sweep of the core files (completed in the Swift reference, June 2026) enumerated every distinct native-128 expression form. The Section 4.2 list is now frozen (D12). All expression forms the sweep found are now vocabulary members: the sign-mask/conditional-negate idiom resolved into `subAbs_d128swap_128x128` (D14), the native `quotientAndRemainder` sites into the divRem family (D15), and the one signed `Int128` accessor (`d128_coeffSigned`) proved dead and was deleted. With the rrmp10 kernels promoted (D16), core contains no native 128-bit arithmetic outside `verify` closures — the confinement rule holds without exemptions. One member the sweep froze *in* later proved to have no consumer and was retired: `xor_128_128x128`, deleted across all four cores by the post-implementation census (D31).

## 6. Signatures, Signedness, and Multi-Value Return

### 6.1 Signed Dwords at the API

Per parent Section 4.3, dwords are signed 64-bit integers on every core, and this layer is where the consequences concentrate: every unsigned compare, logical right shift, division, and high-word check that the signed representation obscures is spelled out *here*, inside primitive bodies, and nowhere else. Uniform API signatures use the platform dword type (`Int64`/`int64_t`/`Long`/`long`), `Int` for counts, lengths, and powers, and `Bool` where the contract is genuinely boolean.

The Swift core is now signed-native: the migration completed across D27–D29 (Decision Log) and changed spellings, not behavior — the dwords are bit-buckets either way, and the signed flip is byte-free (`Int64(bitPattern:)` is a reinterpret, held to a per-function whole-build asm gate throughout). Unsigned semantics are reached only through the named tier-0 ops (`ushr_64_64`, `ucmp_int_64x64`, `udiv_64_64x64`/`urem_64_64x64`, `umulHi_64_64x64`, `hi32_64`/`lo32_64` — all `Int64`-in/`Int64`-out) and the masking shifts `&<<`/`&>>`. The sole remaining `UInt64` in core is the public `Decimal128.init(unsigned value: UInt64)` constructor, a deliberate unsigned-construction entry point.

### 6.2 The Unsigned-Idiom Inventory

The parent Section 4.3 "cast inventory" exists in production form in the Kotlin implementation and is adopted as this layer's reference idiom set for JVM-family bodies:

| Need | JVM-family idiom |
|---|---|
| unsigned less-than | `(x xor Long.MIN_VALUE) < (y xor Long.MIN_VALUE)` |
| carry detect after add | `carry = if (unsignedLT(sum, a)) 1L else 0L` |
| branch-free nonzero mask | `((dw or -dw) shr 63)` (and `.inv()` for the zero mask) |
| branch-free conditional subtract | `adjust = ((rHat - denom) shr 63).inv(); q = qHat - adjust; r = rHat - (adjust and denom)` |
| two-word bitLen, branch-free | `128 - nlz1 - (nlz0 and dw1IsZeroMask)` |

Swift and C bodies achieve the same with explicit unsigned casts (`UInt64(bitPattern:)`, `(uint64_t)`), per parent sanctioned divergence #4. The `carryBitOf(carryFlag)` Bool→64-bit helper of parent Section 4.5 lives here, in JVM-family bodies, and is expected to be absent on Swift/C.

### 6.3 Typed Result Aggregates

Multi-value returns use **typed result aggregates** with positional initializers — the Quot* family — resolving the typed-but-many (Swift Quot*) versus untyped-but-single (Kotlin `Pentad`) design fork in favor of typed. Field meaning lives in the type, not in per-call-site convention; the types cross by each platform's result mechanics — value-return on Swift/C, caller-supplied fill-in on the JVM family (Section 6.4); and proliferation has a natural ceiling — the family is closed over the quotient/remainder/residue shapes the layer actually produces.

The family, with producers:

| Aggregate | Fields | Produced by |
|---|---|---|
| `Quot64Rem64` | q64, r64 | `divRem_q64r64_64x64x64_mu_barrettStep` (primitive, D10) |
| `Quot128Rem64` | q128, r64 | `divRem_q128r64_128x64` (primitive) |
| `Quot128Rem128` | q128, r128 | `divRem_q128r128_128x128` (primitive, D15); core division strategy |
| `Quot256Rem64` | q256, r64 | `divRem_q256r64_256x64` (primitive) |
| `Quot256Rem128` | q256, r128 | core division strategy |
| `Quot128Residue` | q128, residue | `divPow10_q128res_128/256_rrmp10` (primitive, D17); core division strategy |
| `Quot256Residue` | q256, residue | core division strategy |
| `Diff128Swap` | diff128, swapped | `subAbs_d128swap_128x128` (D14) |
| `Diff256Swap` | diff256, swapped | `subAbs_d256swap_256x128/256`, `fusedMulPow10SubAbs_d256swap_*` (D2, D4) |
| `Stripped128StripCount` | stripped128, stripCount | `strip_s128sc_128` (D18, D20) |

The aggregate *types* are defined once with uniform names and field order on all platforms, with the parent Section 5.2 caveat that JVM field ordering may differ physically for alignment; behavior is identical. Kotlin's `Pentad` is retired at rework; its role survives only as the loose-dword internal idiom of Section 3.4.

**Type ownership.** The primitive layer defines `U128`, `U256`, and every result aggregate — `Quot64Rem64`, `Quot128Rem64`, `Quot128Rem128`, `Quot256Rem64`, `Quot256Rem128`, `Quot128Residue`, `Quot256Residue`, `Diff128Swap`, `Diff256Swap`, and `Stripped128StripCount` (`Quot256Rem256` was retired, D35). The rule is by *shape*: every field is a regime scalar (dwords, U128/U256, Int, Bool — and since D17, `Residue` is a 2-bit Int). Ownership is **not** by producer: several aggregates are produced only by core division strategy today, but they stay with their primitive-layer siblings rather than splitting the family across layers by call graph. (Before D17, `Quot128Residue`/`Quot256Residue` were core-defined exceptions because their `residue` field was a core enum; de-structing the enum dissolved the exception.)

### 6.4 Return Mechanics

Parent Section 5.1's asymmetry is the rule, and it is the largest return-side deviation between the value-struct platforms and the JVM family:

- **Swift and C** return aggregates **by value** in registers, where a value struct is available at no cost.
- **Kotlin and Java** use **caller-supplied fill-in**: the result is a **mutable instance the caller owns and passes in as the first argument**, which the function fills. The instances are drawn from the thread-local pool of parent Section 4.7.3, so the primitive layer allocates nothing on the hot path — *deterministically*, not contingent on a JIT optimization. This makes the JVM-family aggregate **and** magnitude types (`U128`, `U256`, every `Quot*`/`Diff*`/`Stripped*`) **mutable** caller-owned objects, in contrast to the Swift/C value structs.

The destination comes first and scratch/context parameters come last: `op(result, operand…, scratch/ctx…)` (D8). Destination-first keeps the operands positionally identical to the Swift/C value-return line (`let z = op(x, y)` ↔ `op(z, x, y)`), holds the destination at position 0 under varying operand arity, and matches both the existing Kotlin kernels (`sumU64(sum, …)`, `c256SetFma(z, x, y, a, pentad)`) and long C precedent (`memcpy(dest, src)`; decNumber's `decNumberAdd(result, lhs, rhs, ctx)`).

The translation rule is mechanical: value-return on Swift/C corresponds to fill-the-caller's-instance on the JVM family — `let z = op(x, y)` ↔ `op(z, x, y)`.

An EA-driven *value-return by default* on the JVM family was considered (the "P5" refinement of an earlier draft) and **set aside**: C2 escape analysis is not guaranteed to scalarize across the core↔primitive module boundary, nor for the wider aggregates (the five-field `Quot256Residue`), so the caller-supplied pool gives a zero-allocation contract the optimizer cannot revoke. The Swift/C value-return and the JVM fill-in are the two committed forms; there is no EA middle tier.

The primitive layer itself allocates nothing on any platform: Swift/C return in registers, and the JVM family fills caller-owned instances drawn from the thread-local pool.

A narrower form of this mutability already pays off ahead of the full fill-in conversion: where a JVM-family producer's output is a *same-type transform* of an inner result — the inner aggregate with a field or two rewritten, the rest passing through — it mutates the inner instance in place and returns it rather than allocating a second one (D37). Swift/C keep value-return there: a value struct copy has no heap allocation to elide.

## 7. Naming

Function names are identical across all four cores, governed by the segment grammar now codified in parent Section 8 — it originated here as D9, and the parent is the authority. This section restates it with the layer-specific notes.

**The segment grammar — result first:**

```
name     ::= op '_' result '_' operands [ '_' qualifier ]
operands ::= width ('x' width)*
result   ::= width | aggregate segment (q256r64, q128res, d256swap, …)
```

The result leads the name so that name order mirrors call-site order on every platform: `let z = mul_256_128x64(x, y)` on Swift/C and `mul_256_128x64(z, x, y)` under the JVM fill-in convention (Section 6.4, D8) both put the result leftmost. Examples: `mul_256_128x64`, `divRem_q256r64_256x64`, `subAbs_d256swap_256x128`. Result-aggregate segments use the established terse forms (`q256r64` = Quot256Rem64, `q128res` = Quot128Residue, `d256swap` = Diff256Swap).

**Full segment form is used throughout the uniform API.** A type-prefix abbreviation (`u128Add`, `u256Mul128x64`) was considered for operations whose prefix fully determines the signature, and rejected: one grammar everywhere keeps the result visible at every call site, keeps every name mechanically parseable for the translation tooling, and avoids a mixed-style API surface. The division contracts show the payoff: a `q64r64` result segment versus `q128r64` over the same `_128x64` operands would state a quotient-fits precondition in the name itself, where a bare `_128` suffix once said it by private convention.

**Tier-0 names** follow the same grammar (D11): `umulHi_64_64x64`, `udiv_64_64x64`, `urem_64_64x64`, `ucmp_int_64x64`, `ushr_64_64`, `clz_int_64`. The `u` op prefix marks unsigned semantics, needed at the dword width where the signed representation makes it ambiguous; the earlier inline-width short forms (`unsignedMul64Hi64`, `clz64`) are retired.

The reconciliation is complete for the primitive layer: the type-prefix spellings (`u256DivRem64`, the `calcBitLen128` family, `mul_128_pow10_p128`) renamed to the full grammar (D9–D22), and the method-form U256 operations became top-level spellings. What remains is core-side and follows the "when touched" rule: the core division-strategy wrapper names (`div_256_pow10_q128res_barrett` and kin) still carry their result segment in third position and reorder to result-first with the exponent folded into the op (`divPow10_q256res_256_barrett`, parent Section 8) when touched; Kotlin's `umul128x128to192`-style kernels are platform-internal decomposition (Section 3.4) and may follow at leisure.

## 8. Per-Platform Implementation Notes

### 8.1 Swift

Tier 0 is native; tier-1 bodies use `UInt128` freely (sanctioned). U128 is physically `UInt128` with computed dword accessors (Section 5.2). Carry/borrow chains use `addingReportingOverflow`/`subtractingReportingOverflow`; full products use `multipliedFullWidth`; `dividingFullWidth` backs the q-fits division steps inside the simple-division kernel ladder. The simple-division kernel ladder (Section 4.4) is the Swift decomposition reference. Primitive sources live beside core sources in the same module until the layering split lands; the earlier premature target split is not repeated until this spec settles.

### 8.2 C

Structs of `int64_t` dwords; bodies cast to `unsigned __int128` and back, with the compiler expected to fuse pack/unpack. `clz_int_64` guards the `__builtin_clzll(0)` undefined case explicitly. The C core does not yet exist; this layer is where its implementation starts, because the Swift-over-C and Kotlin/Native-over-C wrappers let the existing test suites drive it immediately. MSVC's lack of `__int128` is noted in Open Items.

**Implementation status (third port, June 2026).** The C *primitive layer* is implemented and complete — every Section 4.2 uniform-API entry exists, as a CMake/CTest project (C11, `decimal128-c`, headers in `primitive/include`, bodies in `primitive/src`). Unlike the JVM family, C is **close to Swift, not to Java/Kotlin**: tier 0 is native, the `unsigned __int128` extension backs all 128/256-bit arithmetic, and results are **returned by value** (structs), so the fill-in conversion pending for Java/Kotlin does not apply. Each family is conformance-tested against **GMP** (`libgmp`), linked into the test targets only. The C *core* does not yet exist; like Java, it begins from this layer.

The port surfaced findings worth recording:

- **Native `__int128` collapses the division side the JVM family had to build by hand.** 128/64 and 128/128 divide directly (`x / y`, `x % y` on `unsigned __int128`), so there is **no `divlu`/Knuth D and no normalized single-digit step** — the Java note's prediction that "the C core will hit the same gap and want the same shared `divlu` helper" does **not** hold, because `__int128` *is* the `dividingFullWidth` equivalent. The simple-division unit (Section 4.4) is likewise just the plain 4-step base-2⁶⁴ long division (`(carry:limb) / y` per limb); Swift's narrow-divisor kernel ladder (`divMod{64,128,192,256}x{16,32}`) is JVM-targeted tuning and is omitted.
- **The 128-bit shift hazard is UB, not masking.** Where the JVM masks shift counts (`x >>> 64` == `x >>> 0`), C's `unsigned __int128` shift by ≥ 128 is *undefined*. `shr_256_256` branches on `n < 128` vs `n ≥ 128` and never spells `128 - n` at `n == 0` — the same guard the Java kernels need, for a different underlying reason.
- **Top-bit-set 64-bit table literals need a cast.** clang's `-Wconstant-conversion` rejects a bare `0x8000…ULL` initializer for an `int64_t`, so the generated POW10/POW10_256/POW5/RRMP10 tables emit `(int64_t)0x…ULL`. This is the C mirror of Kotlin's hex-`Long`-range problem (opposite cause: clang warns on the narrowing, Kotlin rejects the literal outright).
- **`impossible` is `_Noreturn void` over `abort()`.** The does-not-return contract (sanctioned divergence #7) realized via `abort()` (SIGABRT). Because a signal-terminated process cannot be caught in-process and CTest's `WILL_FAIL` does not invert signal termination, trap tests use **fork-based death tests**: each trap runs in a forked child whose abnormal exit the parent asserts.
- **Byte-packed lookups carry no sign hazard, but keep the Int accessors.** C's `uint8_t` is unsigned, so `RRMP10_LOOKUP_*` element reads need no `& 0xFF` (unlike Java's signed `byte`); the `rrmp10Lookup*` accessors are kept anyway as the uniform-API surface D16 mandates, trivial here.
- **`__builtin_clzll(0)`/`__builtin_ctzll(0)` are undefined** — both leading-zero (`clz_int_64`) and trailing-zero (the `strip` ntz) sites guard zero explicitly, the C-only concern Section 8.4 flagged.
- **GMP oracle, with one digit-count subtlety.** Exhaustive limb sweeps cross-check against `mpz`; the rrmp10 suite drives `(digitLen, K) → pIndex` through the lookup tables exactly as core will, spanning all four residues. `mpz_sizeinbase(x, 10)` is documented to overshoot by one for non-power-of-2 bases, so the digitLen oracle counts via `mpz_get_str` instead.

### 8.3 Kotlin Multiplatform

Tier 0 is the four unsigned-operation expect/actuals from `XPlatform.kt` (renamed per D11 at the rework), plus `clz_int_64` (which may realize as common-source `countLeadingZeroBits` rather than expect/actual — tier 0 is contract, not mechanism). Tier-1 kernels are common source shared by JVM, Native, and JS targets, evolving from `SumU64.kt`. The rework retires `Pentad` (Section 6.3) and the `steal` cache (D7). JS performance rests on emulated Longs and is measured, not assumed (Open Items).

**Implementation status (second port, June 2026).** The Kotlin *primitive layer* is implemented and complete — every Section 4.2 uniform-API entry exists, as a Kotlin Multiplatform module with **JVM and Native (macosArm64) targets live** (JS deferred, Open Items; package `com.decimal128.decimal128kotlin.primitive`). It was ported from the regime-clean Java port (near-mechanical Java→Kotlin) using the legacy `XPlatform`/`SumU64` only for the tier-0 idiom; `Residue` is a plain `Int` (D17, the legacy value-class dropped), `Pentad`/`steal` are gone. The Kotlin *core* does not yet exist. Like Java, it is spelled value-return for now and shares the pending fill-in conversion (Section 6.4).

The port confirmed the multiplatform thesis and surfaced findings:

- **Most of tier 0 is common, not expect/actual.** Kotlin's `ULong` (for `udiv`/`urem`) and stdlib bit ops (`countLeadingZeroBits` for `clz`, `ushr`, `countTrailingZeroBits` for the D21 ntz consumers) realize the bulk of tier 0 identically on every target in `commonMain`. Only **`umulHi` genuinely needs an `expect`/`actual`** — a JVM intrinsic (`Math.unsignedMultiplyHigh`) versus a portable 32-bit decomposition (`umulHiPortable`) on every non-JVM target — so the mechanism is exercised by exactly the one op that diverges, a sharper outcome than the legacy's four expect/actuals. (The legacy used expect/actual for all four for historical/perf reasons; `ULong` div/rem on the JVM already lowers to `Long.divideUnsigned`, so there is no divergence to justify it.) **The non-JVM body is settled as the software decomposition (D43)** — Native, JS, and wasm all share `umulHiPortable`; cinterop and compiler-builtin high-multiply are deliberately ruled out, so JVM is the only target that drops to a platform op.
- **`ucmp_int_64x64` must be spelled explicitly.** Kotlin's `compareTo` guarantees only *sign*, not magnitude, so the −1/0/+1 contract is written `if (unsignedLT) -1 else if (==) 0 else 1` rather than leaning on `compareTo` (unlike Java, where `Long.compareUnsigned` yields exact ±1 for free).
- **Kotlin range-checks hex `Long` literals.** A top-bit-set literal like `0x89AB…L` is "Value out of range" (Java accepts the full 64-bit pattern), so limb-table constants and limb test data use the `0x…uL.toLong()` bit-pattern form. The generated POW10/POW10_256/RRMP10 tables emit this uniformly.
- **`impossible` returns `Nothing` and throws `IllegalStateException`** (vs Swift `-> Never` / Java `AssertionError`) — the same does-not-return contract, a different exception spelling (sanctioned divergence #7 family). Trap tests assert `assertFailsWith<IllegalStateException>`.
- **Cross-platform testing via a multiplatform BigInt oracle.** A shared `testsupport` Kotlin Multiplatform module carries a portable BigInt (from the legacy test sources, made self-contained — its `umulHi` kept independent of the layer under test) so the *exhaustive* property suites run from `commonTest` on **both JVM and Native**, not just JVM. This closes the gap the Java port had: e.g. `umulHi`'s exhaustive cross-check now runs the portable decomposition on Native (on JVM it resolves to the intrinsic), and the rrmp10 quotient/residue and every division trap are verified on Native. The only JVM-only test is the oracle's own `java.math.BigInteger` cross-check inside `testsupport`. (One oracle bug found and fixed: BigInt `divRem`/`divModUIntHelper`/`divModULongHelper` returned the divisor as the remainder for a zero dividend; the `/` and `%` operators were correct, so it was invisible until used.)
- **Java → Kotlin stayed near-mechanical** through the hardest code (the `divlu` 128/64, the 128/128 normalized step, the rrmp10 carry-save kernels). The recurring idiom swaps: `>>>`→`ushr`, `Long.divideUnsigned`→`udiv_64_64x64`, `Long.numberOfTrailingZeros`→`countTrailingZeroBits`, `Long.compareUnsigned`→`ucmp_int_64x64`/`unsignedLT`, and Swift's `inout` rrmp10 bundle / Java's `KState` becomes a small mutable Kotlin class.

### 8.4 Java

Tier 0 as `static` wrappers over `Math.unsignedMultiplyHigh`, `Long.divideUnsigned`/`remainderUnsigned`/`compareUnsigned`, `Long.numberOfLeadingZeros`. Tier-1 source mirrors the Kotlin kernels statement for statement.

**Implementation status (first port, June 2026).** The Java *primitive layer* is implemented and complete — every Section 4.2 uniform-API entry exists, JVM-only for now (package `com.decimal128.decimal128java.primitive`, JDK 21), each family conformance-tested against `BigInteger` (and the Swift `PrimitiveTests` suite is ported and passing). It is the first port of the frozen Swift reference, and it validated the thesis of this document: the regime translated cleanly, with divergences landing exactly where Sections 5–9 predicted (signed-`long` limbs through the §6.2 idioms, flat tables). The Java *core* does not yet exist; like C, it begins from this layer.

**One spelling to convert.** The first port spelled the aggregate and magnitude types as *immutable, value-returned* objects — following the earlier draft's EA-value-return refinement. That refinement is now retracted (Section 6.4): the JVM convention is caller-supplied fill-in (mutable result, passed first, drawn from the thread-local pool). Converting the Java port from value-return to fill-in is pending (Open Items); it is mechanical — every function gains a leading destination parameter and fills it instead of constructing and returning — and the conformance tests pin the behavior across the change.

The port surfaced findings worth recording for the C/Kotlin ports that follow:

- **Tier 0 is a 1:1 intrinsic map, and two contracts come for free.** `Long.compareUnsigned` returns exactly `-1/0/+1` (it delegates to `Long.compare`), meeting the `ucmp_int_64x64` contract with no `signum` normalization; `Long.numberOfLeadingZeros(0) == 64` meets the `clz_int_64` contract with no zero-guard — the explicit `__builtin_clzll(0)` guard is a C-only concern (Section 8.2).
- **`impossible` is `throw impossible(...)`.** It always throws but is *declared* to return `AssertionError`, so a value-returning site can write `throw impossible(msg)` to satisfy Java's definite-return analysis. This is the Java spelling of Swift's `-> Never` (parent sanctioned divergence #7).
- **Shift-count masking is a real kernel hazard.** Java masks shift counts to the low 6 bits, so `x >>> 64` is `x >>> 0`, not `0`. Every synthesized 128-/256-bit shift must branch on `n < 64` vs `n >= 64` and never spell `>> (64 - n)` at `n == 0`. Swift/C native 128-bit types hide this; the JVM-family kernels (and the C 64-bit-limb fallback for MSVC) must guard it.
- **The byte-packed lookups are exactly why D16 mandates Int accessors.** Java's `byte` is signed and the RRMP10 lookup values exceed 127 (up to `0xED`), so a direct element read is negative; the `& 0xFF` zero-extension *inside* `rrmp10Lookup128`/`_256_34`/`_256_38` is load-bearing on the JVM. This is the concrete confirmation of the D16 sub-dword-table refinement.
- **The quotient-fits contract that left the uniform API still exists as a shared interior.** `divRem_q64r64_128x64` was deleted from the inventory (no core consumer), but the 128÷64 q-fits *operation* it named is needed internally by both the 128- and 256-bit division units. Java has no `dividingFullWidth` intrinsic, so it is realized once as a package-private `divlu` (Knuth Algorithm D, two corrected 32-bit digits) shared by both. The C core will hit the same gap and want the same shared helper.
- **D15's "no full Knuth D for 128÷128" held.** A divisor `< 2^64` delegates to the 128÷64 kernel; a divisor `>= 2^64` is one clz-normalized single quotient digit plus a multiply-back correction — confirmed against `BigInteger`.
- **`ntz` folded into platform-local bodies as D21 predicted** — `strip` and the power-of-two divisor path spell `Long.numberOfTrailingZeros` directly, no uniform name needed.
- **Swift's `inout` bundle becomes a small mutable state object.** The rrmp10 kernels carry a mutable `KState` (round bit, fraction-bits-remaining, sticky compare, quotient limbs) where Swift used `inout` parameters, and the `UInt128` carry-save accumulator becomes a reused two-`long` accumulator with an `accAdd` helper.
