Thoughts and justifications for yet another decimal floating point format. 

DFD == Decode Friendly Decimal or Decode Fast Decimal
formerly TCD == Twos Complement Decimal

BID was not designed for software decoding. 
In hardware it probably is not that bad. 
DFD allows one to store and operate on values in-memory more quickly. 
Represents the exactly the same range of finite values as decimal128. 
Just friendly to decode. 

BID 128 does not use the "large" exponent encoding that is used in BID32/64. 

DFD format
1 sign bit
14 exponent bits in 2's complement [-8192,8192] ... exceeds [-6176,6111]
113 coefficient bits

If the exponent is -8192 then the value is non-finite. 
Use the coefficient to distinguish Inf, qNaN, sNaN. 
qNaN and sNaN have a payload. 
We have 113 bits ... but we only need to support 33 digits
10**33 can be supported in 110 bits. 
So, at first blush we don't have any problems and it will fit. 

Storing the exponent in 2s complement has many advantages

extracting the exponent is a simple shift and mask ... or a bitfield extraction on
some CPUs. 
Positive integer values LT 10**34 have exactly the same representation in DFD,
(although the reverse does not apply because of cohorts)
Negative integer values are sign-magnitude in DFD. 

For addition of finite values, if the top 15 bits are equal then the 
values are aligned and we can perform a simple addition of the 113-bit masked
coefficients. 

The fast path ...
If the result is LT 10**34 we do not have overflow.
We or in the top 15 bits and return immediately. 
This works for 2 + 2, but also for 39.95 + 19.99 ... the qExp is aligned. 

If the result GE 10**34 then we have more work to do. If the operands were finite
then we divide by 10, round, and increment qExp, possibly 

We must perform this rare bounds check. 

What about our special values? 
They all have the same qExp. 
all permutations of INF QNAN SNAN + INF QNAN SNAN
They have the same exponent, so we will add them together. 

For these non-finite values we can choose our coefficient so that they are
guaranteed to generate overflow when encountered in an addition operation. 
If the value is at least 10**34 they they will force overflow. 

For non-finite values the coefficient holds a value of at least 10**34
to ensure overflow on select arithmetic operations.

When we last left our friend _addition/subtraction_ we had taken

If the top 15 bits are different, then we can compare the two qExp. 
If they are aligned, then the two signs are differ and we are performing
a subtraction. 
We subtract one from the other. 
Generally that means we look at the magnitudes and subtract the 
smaller magnitude from the bigger one. 
But, we aren't going to do that. 
We are going to performed a _signed_ subtraction in order to get a signed
difference. If it was positive then we lucked out and the result has the sign
of the minuend. If it was negative then the result is the sign of the
subtrahend. We can find a fast way to get the sign correct for the difference. 

The problem is (catastrophic) cancellation. 
NaN - NaN => goes to zero and we did not detect it.

We are left with the problem of ...

How do we distinguish between INF, qNaN, sNaN?

+/- INF ... no payload ... we only need one state ... we can squeeze it in anywhere. 
let's say that coeff all bits on == INF. It will definitely overflow. 

qNaN and sNaN can each carry a full payload. 
So, once we have determined that it is not a NaN, we need a bit to
distinguish qNaN from sNaN. 

There are 113 bits in the coefficient, for 2^113 unique values. 
We don't want to use [0,10^34) because they will not overflow
2^113 - 10^34 == 3.84E32 ... that is 33 digits, but not a full 33 digits. 
And we still have to have a quiet vs signaling bit. 

A couple of thoughts ...
OPTION1
I suggest that 19 digits fitting in 64 bits is sufficient payload space. 
That allow us to pick easy-to-recognize bit patterns for INF, NAN, isSignaling

OPTION2
restrict everything to the top word and set the bottom word to zero. 
That leaves 0x12f64152783f ==  20,848,867,178,559 slots open. 
divide it by 2 for  q vs s and we still have 13 decimal digits for NaN payloads

OPTION3
If you absolutely *must* have 33 digits of payload, then we need 3 more bits from the bottom of qExp. 
That would say that anything less than -8184 is non-finite.
